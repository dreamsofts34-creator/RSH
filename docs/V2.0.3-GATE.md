
Individual pieces:

```sh
cargo run -p rsh-rig -- --gate [--out DIR]   # 32 rig checks
cargo run -p rsh-gate-ui                     # 6 headless UI checks
cargo test -p rsh-rig                        # 21 rig unit tests
```

clippy (`-D warnings`). It is **not** run by default: the full suite is
the gate coordinator's step and, per user order, runs only at phase
gates, not on every small fix.

## CI follow-up (run 44105260838)

The merge commit's CI run FAILED (6 jobs), even though the local gate
was GREEN 8/8. The local gate never compiled the Windows-only code and
never ran the rig the way CI does, so three failure classes slipped
through:

- **Windows-only compile errors (E0308):** `#[cfg(windows)]` code in
  `port_conflict.rs` (expected `&str`, found `String`; expected
  `PROCESS_NAME_FORMAT`, found integer) and a Unix-only bind in the
  fake daemon never compile on the Linux gate box. Fixed by Teams A+B
  in parallel worktrees (not this one).
- **cargo audit — chrono advisory:** an advisory hit on chrono;
  fixed by Team C.
- **rig-gate CI setup gaps (this team's fix):** the rig-gate job ran
  `cargo run -p rsh-rig -- --mode quick` → 59/68 PASS; the 9 F17
  failures were ALL environment/setup gaps, not product bugs:
  `gate-respawn-bound` ("xdotool missing"), `gate-ipc-bind-failure` +
  `gate-hung-daemon` ("target/debug/rsh-daemon not built"),
  `gate-already-running-race`, `gate-xvfb-hidden-shown`,
  `gate-rapid-reconnect`, `gate-toast-dedupe-integration`,
  `gate-lifecycle-soak` ("staging failed"), `gate-frame-budget`
  ("Xvfb did not start"). The local gate passed because
  `tools/gate-checks/run-gate.sh` builds the binaries first and this
  box has Xvfb + xdotool installed; the CI job installed only
  libudev-dev and never built the binaries.

Fixes (branch `v2.0.3-ci-fix/ci-rig`, commit in the coordinator's
report):

- `.github/workflows/ci.yml` rig-gate job: installs the X stack the rig
  needs (`xvfb xdotool libxkbcommon-x11-0 libxcb-xkb1 libxdo3
  libxtst6`, alongside libudev-dev) and builds the lifecycle binaries
  (`cargo build -p rsh-ui -p rsh-daemon -p rsh-fake-daemon`) before the
  rig runs. Staging requirements verified against
  `tools/rsh-rig/src/lifecycle_checks.rs`: it invokes only `Xvfb` and
  `xdotool` (via `which` in `XvfbSession::start`), needs the xkbcommon
  libs for winit startup, and stages `target/debug/{rsh-ui,rsh-daemon,
  rsh-fake-daemon}`. The job stays FAIL-CLOSED: no skips, no `|| true`,
  no continue-on-error.
- Gate hardening — new `windows-check` step in
  `tools/gate-checks/run-gate.sh`, in the DEFAULT gate path (not only
  `--full`, since this class already slipped through once):
  `cargo check --workspace --target x86_64-pc-windows-msvc`
  (check-only, no linking). If the target is missing it is installed
  via `rustup target add`; if rustup/the target is unavailable the
  step FAILS with a clear message — it never silently skips.

  Verification on the unfixed tree (this session):
  - The step runs, finds the target already installed, and FAILS
    LOUDLY (exit 101). The error class itself IS catchable on this
    box, proven by targeted checks that avoid ring's build script:
    `cargo check -p rsh-transport --target x86_64-pc-windows-msvc`
    → 2× E0308 in `crates/rsh-transport/src/port_conflict.rs:267`
    (expected `&str`, found `String`) and `:297` (expected
    `PROCESS_NAME_FORMAT`, found integer) — exactly the CI failure;
    `cargo check -p rsh-fake-daemon --target
    x86_64-pc-windows-msvc` → E0425 (`bind_unix_socket` not found in
    `rsh_ipc` on Windows) + E0599 — the Unix-only bind class.
  - COORDINATOR DECISION (2026-11-17): the step is scoped to
    `--workspace --exclude rsh-app`, proven GREEN on the merged
    fix tree (`cargo check --workspace --exclude rsh-app --target
    x86_64-pc-windows-msvc`, exit 0). `ring` enters ONLY via rsh-app
    (tauri-plugin-updater → reqwest → hyper-rustls → rustls → ring);
    its build script needs MSVC `lib.exe`, which no Linux gate box
    has. The exclusion matches the gate's existing `--full` Linux
    clippy/test steps, which already exclude rsh-app; rsh-app's
    Windows compile is covered by CI's tauri-build job on a real
    Windows runner. A full `--workspace` check would need a Windows
    cross-toolchain (e.g. cargo-xwin) — a future improvement, not a
    hotfix blocker.
