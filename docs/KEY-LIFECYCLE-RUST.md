# RSH — Key Lifecycle Design (Rust series, v1.0.0)

**Status:** DESIGN — no implementation yet. This document designs; it implements
nothing. Code comes in Phase C (pairing / control channel), Phase D (firmware),
and the Release phase (signing), per this design and its open-item list.
**Date:** 2026-11-14
**Series:** App Rust **v1.0.0** (fresh start, no port of C# code) · Firmware
**C++ v4.0.1** (Track A ships v1.0.0; Track B esp-rs is a spike only) ·
Protocol **v2.1 wire FROZEN** (byte-level authority: `PROTOCOL-V2.1.md`).
**Authority:** `RSH-RUST-ARCHITECTURE.md` §2.5 (security model) · `RSH-RUST-PLAN.md`
D-R9 (keyring), D-R10 (OTA signing), D-R11 (OV deferred) ·
`SECURITY-INPUT.md` §2 (key lifecycle), §4 (OTA signing), §8 (carried items).
**C# baseline (read-only reference):** `reference/docs/KEY-LIFECYCLE.md`,
`PROTOCOL-V2.1.md` §4–§5, `SIGNED-OTA.md`, `SECURITY.md` (C# app v2.0.4 /
firmware v4.0.1). Where this document and a C# document disagree, this
document wins for the Rust series — and the disagreement is recorded, not
hidden (§14, §15).
**Companion document:** `THREAT-MODEL-RUST.md` (STRIDE; the mitigations here
are the defences for TM-W01–W08, TM-O01–O04, TM-P01–P05, TM-R01–R08 there).

> **One-line summary:** one random 32-byte key per board, generated by the
> board on first boot, disclosed exactly once inside a 60-second pairing
> window, stored on the PC only in the OS credential store, never exported,
> never logged, and replaced only by a physical KEY_RESET — or by re-pairing
> after the documented C# → Rust breaking change (§10).

---

## 0. Principles (carried from C#, locked for Rust)

1. **No factory.** The user flashes the board at home. No factory-provisioned
   key, no shared default password, no cloud account, no key-escrow service.
2. **One key per board, random.** The key is per-device, never shared between
   boards, never derived from the MAC (the MAC is public — deriving a secret
   from it is forbidden, C# R-H10 carried).
3. **The board makes its own key** — on first boot, from its hardware RNG.
4. **The key is disclosed exactly once** — in the first HELLO, inside the
   60-second pairing window. After the window it is never sent again.
5. **The PC stores the key in the OS credential store** (§4) — never in a
   plain file, log, UI, crash dump, telemetry payload, or settings export.
6. **No shared defaults** (NIST IR 8259A secure defaults).
7. **DTLS is deferred, by decision** — local AP + HMAC v2.1 is the design, not
   an oversight (carried from C#; see `THREAT-MODEL-RUST.md` §1, assumptions).
   Transport protection therefore rests on AP isolation + HMAC + the pairing
   window, and the residual risk is stated honestly (§15, THREAT-MODEL §6).

## 1. Secrets inventory — what exists, what each one protects

| Secret | Size / form | Generated by | Stored where | Used for |
|---|---|---|---|---|
| **Device key** (control-channel key) | **32 bytes (256-bit) — locked** (§2) | Board, first boot, hardware RNG | Board: NVS (§12). PC: `keyring`, service `RSH`, username `board:<boardMac>` (§4) | HMAC-SHA256 over `nonce ‖ counter ‖ cmd ‖ payload`; tag = first 16 bytes (protocol v2.1, D3) |
| **Wi-Fi / OTA password** | 24 chars, 57-symbol charset (§8) | Board, first boot, hardware RNG | Board: NVS (obfuscated in C++ v4.0.1 — see §12). | **Secure Boot key** | RSA-3072 key pair | Offline, release process (C# series keypair exists; SBV2 digest `1bb10ab7…551e9`) | Public digest only, in eFuse; private key offline, never in repo | Only images signed with this key boot |
| **Firmware image signing key** | Ed25519 key pair | Offline, release process — **existing keypair REUSED, no new keypair** | Private key in `~/workspace/projects/rsh/signing-keys/` (outside repo, 0600) and CI secret `RSH_SIGNING_KEY_PEM`; public key baked into firmware | App-side + board-side verify-before-apply of firmware images (§13) |
| **Tauri updater signing key** | Ed25519 key pair — **dedicated, separate from the firmware key** | `tauri signer generate` (new keypair for the Rust series) | Private key in GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY` (+ password secret if passphrased); public key baked in `src-tauri/tauri.conf.json` (`plugins.updater.pubkey`) | Tauri updater verifies update manifests before install (§13) |

**Key separation (locked, D-R10 / SECURITY-INPUT §6.1):** firmware signing key,
Tauri updater key, and the (deferred) OV code-signing certificate are **three
different keys, never substituted for each other**. Compromise of one leaves
the other two unaffected. The three keys are never in the same place, never
in the same CI job unless that job needs exactly one of them, and never in
the repo, git history, a container image, or chat.

**Public-key fingerprint (firmware signing, carried from C#):**
`SHA-256 387764a4529337c437b233a148b48f9b2ffe3f3b5015e14c95737cb3a67a6411`.
The Rust release workflow reuses the same secret (`RSH_SIGNING_KEY_PEM`;
name may change in the Release phase — the secret itself does not).

## 2. First flash / first boot — how the key is made

1. The user flashes firmware v4.0.1 onto the board over USB-serial.
2. On **first boot**, firmware looks in NVS for a device key.
3. **No key found:**
   - The board generates a new random **32-byte** key from its **hardware
     RNG**. Key length is **locked at 32 bytes** in the Rust series
     (C# OPEN-2 is CLOSED by this decision; HMAC-SHA256 needs 256 bits).
   - The board writes the key to NVS (§12 for the plaintext/encryption
     status — do not claim encryption until OPEN-3 closes).
   - The board generates the 24-character Wi-Fi/OTA password (§8) and
     stores it in NVS.
   - The board marks itself **unpaired** and opens the **pairing window
     (60 s)**. The window starts when the AP comes up (boot fail = AP not
     up within 15 s, D29 — carried).
4. **Key found:** the board boots paired; no new key is made; no pairing
   window opens; HELLO never carries the key again.
5. A new key is generated **only** on: KEY_RESET (§5), or a full NVS erase
   followed by reflash (§7). **Never** on routine reboot, firmware OTA
   update, or FACTORY_RESET.

**Key-generation failure — fail closed (C# OPEN-4 rule carried):** if the
hardware RNG is not ready, or generation fails, or the generated key is
weak/repeated, the board **must not boot forward with that key**. Retry /
error-blink behaviour is a Firmware-phase (Phase D) definition; the design
rule is only this: *no boot proceeds on a weak or repeated key*.

## 3. Pairing flow — step by step

Pairing is the one-time exchange of the device key + Wi-Fi/OTA password
between board and PC app. Only an unpaired board pairs, only inside the
60-second window.

| Step | Who | What happens |
|---|---|---|
| 1 | Board | First boot (§2): key + password generated, saved in NVS, unpaired state, 60 s pairing window opens, AP up. |
| 2 | User / app | **Bootstrap (OPEN-6 — DECIDED, see below).** The PC connects to the board. The **primary** bootstrap is **wired USB-serial pairing**: the same v2.1 HELLO (92 B fixed) runs over the `RSHS` serial framing at 921600 baud, with the same session/auth rules as Wi-Fi (protocol v2.1 §10; C# OPEN-20 carried — both transports, Wi-Fi primary for data, wired as the pairing trust anchor). The **fallback** is the open-AP bootstrap: for the first pairing only, the SoftAP is open (no password yet — the password is itself part of what pairing delivers). The fallback carries a **USER-GUIDE warning**: pair only at home, in your own room, never on shared/public Wi-Fi; the open window is 60 s and proximity-bound. |
| 3 | App | The app sends HELLO with **session flag = new session** (D30). |
| 4 | Board | HELLO reply: **new nonce (16 B)** + — only in this first HELLO, only inside the window — **device key (32 B)** + **Wi-Fi/OTA password (24 B)**. Outside the window, or after pairing, those fields are zero. |
| 5 | App | The app stores the key **immediately** in `keyring` (§4) and the password in its `board:<boardMac>:wifi` entry. The password is shown **once** as a QR / label (§8) and never in plain text again. |
| 6 | App | The app confirms pairing: HMAC-signed GET_CAPS (new nonce, counter 0 — D3/D30). The board verifies the tag; OK means pairing succeeded. |
| 7 | Board | On successful confirmation (or when the window expires) the board marks itself **paired**. From then on HELLO carries only a nonce — never the key. |
| 8 | On failure | If GET_CAPS fails inside the window, the app may retry (new HELLO, new session). After the window closes, pairing is over — re-pairing needs KEY_RESET (§5). |

**Why the wired-primary decision (OPEN-6):** the open-AP bootstrap leaves the
one-time key disclosure protected only by proximity + 60 seconds (TM-W02,
the largest open point in the C# model). A USB cable is a physical trust
anchor the attacker cannot reach from Wi-Fi range: the key never crosses the
air on first pairing when the user pairs over cable. The open AP remains
available as a fallback for users without a cable handy, but it is the
second choice, not the default path, and the USER-GUIDE warning is mandatory
— not optional documentation. This decision closes OPEN-6 for the Rust
series; the fallback's residual risk stays on the books in
`THREAT-MODEL-RUST.md` (TM-W02, residual Medium-High on the fallback path
only) and is not hidden.

**After the window — SEC-R2-03 DECISION (recorded here, enforced in
Firmware/OTA phase):** when the 60-second window expires on an unpaired
board, the AP **moves to WPA2 with the generated password** — it is **not**
left open, and it is **not** closed. Reason: closing the AP would strand the
board (the only recovery would be KEY_RESET, which punishes a user who
simply missed the window), while leaving it open indefinitely was the
original defect (SEC-R2-03, Medium). WPA2-with-generated-password keeps the
board reachable for a later pairing attempt (the user reads the password
from the board label / pairs over USB-serial) while removing the
indefinite open-AP exposure. The generated password is the one from §8;
until the user pairs, the board stays unpaired and HELLO still discloses
nothing. Implementation (AP state machine) is a Firmware/OTA-phase task;
this document records the decision and its reason so the phase cannot
re-decide it silently.

**Channel discipline:** the transfer channel is the board's own SoftAP
(local link, no internet, no cloud) or the USB cable. An attacker needs
(a) to be in Wi-Fi range, (b) joined to the AP, and (c) inside the 60 s
window — all three. Disclosure is once-only; after the window the board
refuses key requests. After the transfer, all control traffic is
HMAC-signed (§1) — the key is never exchanged again.

**HELLO frame (frozen, protocol v2.1 §2.2):** 92 B fixed; nonce 16 B;
deviceKey 32 B + wifiPassword 24 B only when unpaired + inside the window,
otherwise zero. The Rust implementation must match the C#/C++/Python golden
vectors byte-for-byte (Phase A1 gate).

## 4. App-side storage — `keyring` (Windows Credential Manager, DPAPI-backed)

- **Crate:** `keyring` 3.x (pin the exact version at build start — D-R9;
  SECURITY-INPUT notes a 3.x vs 4.x open item; the crate choice is locked,
  the minor version is pinned when building starts). Its Windows backend is
  **Windows Credential Manager** (`CredRead`/`CredWrite` via FFI),
  credentials **DPAPI-encrypted, current-user scoped**. This is the Rust
  equivalent of the C# DPAPI CurrentUser store — **equal, not stronger and
  not weaker**: the same limit applies (TM-P01 residual Medium — malware
  running as the same Windows user can open the key; see §4.3 and
  `THREAT-MODEL-RUST.md` TM-P01).
- **Naming (locked, SECURITY-INPUT §2.2):**

  | Entry | Service | Username |
  |---|---|---|
  | Device key | `RSH` | `board:<boardMac>` |
  | Wi-Fi / OTA password | `RSH` | `board:<boardMac>:wifi` |

  One board = separate entries. A different board never overwrites an
  existing board's entry (this is part of the SEC-R2-06 board-binding fix,
  §11 of the threat model — a stored key is only replaced after user
  confirmation when the BoardMac differs).
- **Where the store lives:** the OS credential store — **not** a file under
  `%AppData%\RSH`. No key material is ever written to a file by the app,
  in any format. (Architecture §2.2 S-6 mentions a possible DPAPI-direct
  spike in Phase A3; the design decision here is `keyring` per D-R9. If
  the A3 spike ever revisited that, this document would need a deliberate
  amendment — the storage mechanism is not to be swapped silently.)

### 4.1 In-memory handling (`zeroize`)

- The key lives in memory only inside a `ZeroizeOnDrop` type (`zeroize`
  crate 1.8.2, `derive` feature) — e.g. a `SecretVec<u8>`-style wrapper.
  It is zeroed on session end and on app exit.
- The key is **never** held in a `String`, never cloned into a `String`,
  never passed through frontend IPC, and never formatted. `Debug`/`Display`/
  `Serialize` impls on secret-bearing types must **mask or omit** the
  secret (ideally no `Debug` at all for the key type).
- The key is never sent across the FFI boundary (vJoy / HIDMaestro get only
  axis/button/report data — SECURITY-INPUT §7.1).
- HMAC tags are compared with **constant-time comparison** (`subtle`
  crate); `==` on a tag is forbidden. The tag itself is never logged — not
  even its first byte.
- The HMAC key is **not** zeroed after every frame (the session needs it),
  but it **is** zeroed at session end / app exit.

### 4.2 Forbidden (carried from C#, no exceptions)

- Key in a plain-text file, log, crash dump, telemetry payload, settings
  export, backup zip, or UI — forbidden. (Telemetry default OFF, D31;
  crash dumps opt-in and redacted.)
- **No key export / backup / cloud sync.** The key lives on this PC only.
  There is no "export my key" feature, and none may be added later without
  a security review and a design amendment.
- Key in the repo, git history, a container image, a screenshot, or chat —
  forbidden. CI secret-scans gate this (Foundation phase).
- Wi-Fi password in `settings.json` (or its Rust equivalent) in plain text
  — forbidden; read it only from the `keyring` entry.
- **Legacy plaintext password (SEC-R2-02): DROPPED with reason.** The C#
  item (lazy wipe of a legacy plaintext Wi-Fi password) does not apply:
  v1.0.0 is a fresh series with no legacy plaintext store. If a C# settings
  import is ever built, password fields are **excluded** from the import —
  re-pairing via `keyring` is the only path.

### 4.3 What the store does and does not protect

- **Does:** the key is not readable from disk by another Windows user, or
  by removing the disk. The OS credential store is user-scoped and
  DPAPI-encrypted.
- **Does not:** malware running as the same Windows user can open the key
  (TM-P01). There is no app-level design that removes this limit; the
  defence is the PC's own hygiene (Windows Update, antivirus, no admin
  rights for untrusted software), and the USER-GUIDE must say so. If the
  user suspects compromise, KEY_RESET (§5) replaces the key and ends the
  exposure.

## 5. FACTORY_RESET vs KEY_RESET — the difference

|  | FACTORY_RESET (cmd `0x08`) | KEY_RESET (cmd `0x0B`) |
|---|---|---|
| **What is wiped** | Only pin map / config (factory defaults) | Only device key + pairing state (+ password, §8) |
| **Key** | **Unchanged — the old key still signs valid HMAC; no re-pairing needed** | **Wiped + new key generated. Old key invalid immediately.** Re-pairing mandatory (§3) |
| **Password** | Unchanged | **New password generated** (§8) |
| **Config** | Wiped (factory defaults) | **Unchanged** |
| **Auth** | Must be HMAC-signed (with the old key) — impossible without the key | **Physical BOOT-hold mandatory** (below). Old key **not** needed — that is the point (the recovery path when the key is lost) |
| **When used** | Bad pin map / config recovery | Key lost, app reinstalled, board given to another PC/person, suspected key compromise |

**KEY_RESET procedure (design rule, protocol v2.1 §4.4 — C# OPEN-8/9/10
CLOSED, values carried):**
1. The user powers the board off, then powers it on **holding BOOT
   (GPIO0)** — proof of physical presence. KEY_RESET is **never**
   software-only.
2. Hold duration at power-up distinguishes the two BOOT-hold uses
   (tolerance ±0.5 s at the edges; Firmware phase measures the real board):
   - Hold < 5 s → normal boot (BOOT ignored).
   - **5 s ≤ hold < 10 s → safe mode** (factory pin map + AP; old
     behaviour). LED: slow blink, 1 Hz. KEY_RESET does **not** happen in
     safe mode.
   - **Hold ≥ 10 s → key-reset-armed state.** LED: fast blink, 4 Hz.
3. The armed state is indicated by the LED fast blink **and** the
   HELLO/GET_CAPS flags bit `keyResetArmed = 1`. The armed window is
   **120 s** from boot; if it expires, the board reboots into normal mode
   and the user must BOOT-hold again.
4. Only in the armed state (and only there) does the app send KEY_RESET.
   Unarmed KEY_RESET is always rejected with `UNSUPPORTED` (6).
5. On success the board erases the old key, generates a **new key + new
   password**, marks itself unpaired, and opens a **new 60 s pairing
   window** (§3). Config is untouched.

## 6. Nonce / counter — per-session rules (D3, D30)

These are **not** key rotation. The key stays the same across sessions;
only the nonce and counter change.

- **Counter is per-session** (u32, monotonic). A new nonce means the
  counter restarts at 0.
- **Nonce rotates only** when the board reboots or the PC requests a new
  session (HELLO with `sessionFlag = 1`). A routine 1 Hz HELO
  (`sessionFlag = 0`) returns the **old** nonce.
- Every control frame increments the counter; on retry the **reqId stays
  the same, the counter is new**; the board recognises duplicates from the
  (reqId, counter) pair (32-entry cache, D3).
- Counter ≤ session max-seen (RFC 1982 serial arithmetic) → `REPLAY` (2).
  Counter wrap `0xFFFFFFFF → 0` is a new value, not a replay.
- When a session ends, the old nonce/counter are never reused. A frame
  signed under an old nonce → `BAD_TAG`.
- **New-session gating (SEC-R2-04, open — fix in Firmware/OTA phase with
  Engine):** an unauthenticated HELO with `sessionFlag = 1` currently
  rotates the nonce and resets both control sessions (DoS vector, Medium).
  The fix is a rate limit on new-session requests (e.g. one new session
  per N seconds, or only when no authenticated session is active). The
  exact limit and its rig DoS test are Firmware-phase work; the rule that
  the limit exists is recorded here and in `THREAT-MODEL-RUST.md` §5.
  It is a DoS only — never a control compromise.

## 7. Key loss / reinstall / PC change / board change — recovery

**Rule:** re-pairing always creates a **new key**; the old key is never
valid again; there is **no "recover the old key" path**.

| Situation | What happens |
|---|---|
| **App reinstall / PC reinstall / key lost from the store** | The app has no key. The board is still paired to the old key and will not disclose a new one. **Fix:** KEY_RESET (BOOT-hold, §5) → board makes a new key → §3 pairing again → old key invalid. Reinstalling the app alone never restores pairing. |
| **New PC, same board** | The new PC's app has no key → KEY_RESET + re-pairing (§5). The key is **never** copied from the old PC to the new one. |
| **Board replaced (new board)** | The new board has its own new key (§2). The app cannot talk to it with the old key. **Fix:** pair with the new board (§3, first boot, 60 s window). The old board's key is never transferred. Profile v2's `boardMac` field (D21) lets the app detect the change — and calibration must be redone (with a warning). |
| **Board reflashed (USB-serial, full erase)** | NVS erased → key gone → new key on next boot (§2 step 3) → §3 pairing again. |
| **Firmware OTA update** | OTA does **not** touch the key NVS namespace — key and pairing survive (confirm in Firmware phase, C# OPEN-11 carried). |
| **User gives the board to someone else** | KEY_RESET **before** handing it over — otherwise the new owner cannot use the board without the key, and the old owner (if they still hold the key) can still control it. This goes in the USER-GUIDE. |
| **Key compromise suspected** | KEY_RESET immediately (§5) — new key + new password + re-pairing. The old key stops working the moment KEY_RESET succeeds. See also §13 (signing-key compromise is a different, Release-phase procedure — OPEN-19 / SEC-H-04). |

**Re-pairing invalidates the old key immediately.** The moment KEY_RESET
succeeds, the old key is erased on the board; any app, script, or attacker
holding it can no longer sign a valid control frame. There is no grace
period and no overlap window in which both keys work.

## 8. Wi-Fi / OTA password provisioning + forced change

- **Random per-device:** the board generates the password on first boot
  (§2 step 3). **Never derived from the MAC** (MAC is public, R-H10).
- **Format (Architecture §2.5, carried):** 24 characters, charset
  `A–Z a–z 2–9` (57 symbols, ≈140 bit). Displayed as **4 groups of 6,
  hyphen-separated**; on the wire and in storage the hyphens are **not**
  present.
- **One credential:** the same password is the AP join password **and**
  the WebOTA password. (Architecture §2.5 states this as the design.
  **Discrepancy flag:** SECURITY-INPUT §5 lists OPEN-13/14 — "one
  credential or two?" — as still to be decided in the Architecture/
  Firmware phase. This document follows Architecture §2.5 (one
  credential) as the design baseline; if the Firmware phase reopens
  OPEN-13/14, both documents must be amended together **before** pairing
  is implemented. The choice must not be changed silently in code.)
- **Shown once:** the app shows the password on first pairing **once** as
  a QR code / label — the user saves or prints it. After that the app
  never shows it in plain text again.
- **Forced change (NIST IR 8259A, C# OPEN-12 carried):** on first setup
  the user is offered/required to set their own password; the factory
  generated password is not meant to last forever. Exact UX (in-app
  change flow via HMAC-signed SET_PASSWORD, board-side apply) is a
  UI/Tauri + Firmware-phase definition.
- **SET_PASSWORD (cmd `0x0C`):** HMAC-signed, mandatory. Length/charset
  8–63 chars, printable ASCII `0x21–0x7E`; app-side 60 s rate limit;
  after a password change the old password is invalid immediately.
- **Password forgotten:** the recovery path is **KEY_RESET** (§5) — it
  resets the key **and** the password together (C# OPEN-16 CLOSED in
  protocol v2.1 §5.4). FACTORY_RESET does **not** touch the password
  (credentials are not config). Reason: password reset needs physical
  presence, otherwise anyone holding the key could lock the owner out.
- **No shared default:** every board's password is different; there is no
  "admin/admin".
- **Board-side storage (C++ v4.0.1):** the password is stored obfuscated
  (`"wifipw2"` — device-key keystream XOR). That is **not encryption** —
  the device key sits in the same plaintext NVS, so a full flash dump plus
  the open-source scheme recovers it. The XOR obfuscation is **not**
  rebuilt in Rust firmware; the real fix is encrypted NVS / flash
  encryption (OPEN-3, §12).

## 9. Key rotation — when it happens, when it never does

**Rotation happens only on:**
- KEY_RESET (§5) — user-initiated, with BOOT-hold.
- Re-pairing after key loss (§7) — which is KEY_RESET in practice.
- Board replacement / full reflash — new board / new NVS = new key (§2, §7).

**Rotation never happens on:**
- Routine reboot, OTA update, or FACTORY_RESET.
- Passage of time (expiry) — the key has **no expiry date**.
- Every session / every HELLO — sessions change only the **nonce and
  counter** (§6), not the key.

## 10. BREAKING CHANGE — C# → Rust v1.0.0 requires re-pairing for every user

**This is a documented breaking change, not a migration gap to be worked
around later.**

- The C# app stored its key as a **DPAPI blob** (app-specific format, file
  under `%AppData%\RSH`). The Rust app stores its key as a **`keyring`
  entry** (Windows Credential Manager, service `RSH`). These are **different
  stores**: Rust v1.0.0 **cannot read the C# key**. (SECURITY-INPUT §2.2
  marks the exact technical impossibility of cross-reading as
  **[UNVERIFIED]** — to be confirmed once in the implementation phase. The
  decision stands either way: **there will be no "import the C# key" path**,
  because that path would itself be a key-leak vector.)
- **Consequence:** every user upgrading from C# v2.0.4 to Rust v1.0.0 must
  **re-pair**: KEY_RESET (BOOT-hold ≥ 10 s, §5) → new key + new password →
  §3 pairing. Old C# keys stop working the moment the user moves to the
  Rust app (the board still holds the old key until KEY_RESET replaces it
  — the board is unchanged, the app is new).
- **Required communication (both are release gates, not nice-to-haves):**
  1. **Release notes (v1.0.0)** — first page, plain language: "You must
     re-pair your wheel: hold BOOT for 10 seconds, then pair again. Your
     old key cannot be carried over."
  2. **USER-GUIDE note** — same instruction, with the BOOT-hold steps and
     the reason (different credential store; no import path by design).
- **Profiles/settings are a separate question** (C# profiles import vs
  fresh start — master plan §9 Q3, DATA-INPUT §8). Whatever that decision
  is, **password/key fields are always excluded from any import** — keys
  and passwords are never carried across, only re-paired.
- **No legacy plaintext store:** Rust v1.0.0 has no legacy password store
  to migrate, wipe, or preserve (SEC-R2-02 dropped — §4.2).

## 11. Board-side storage — firmware dependence

- **Track A (C++ v4.0.1, ships v1.0.0):** the device key is in **plaintext
  NVS** and the password is XOR-obfuscated only. This is the carried C#
  state (SEC-E-01 PARTIAL). It is **not** claimed to be encrypted anywhere
  in Rust documentation. The residual risk is TM-W07 (Medium) until OPEN-3
  closes — see `THREAT-MODEL-RUST.md` §6.
- **Track B (esp-rs, spike only):** if Rust firmware ever ships, encrypted
  NVS is a **day-1 requirement**, not a later phase item (SECURITY-INPUT
  §2.3): with ESP-IDF, NVS encryption (XTS-AES, IEEE P1619) needs flash
  encryption enabled and an `nvs_keys` partition (4 KB minimum, encrypted).
  With bare-metal `esp-hal` / no_std, the encrypted-storage design must be
  re-researched in the Firmware phase — **no claim is made here**.
- **Password obfuscation (`wifipw2` XOR) is NOT rebuilt in Rust firmware.**
  It only defeated a casual `strings` scan; it was never encryption.
  Rust firmware gets either encrypted NVS or no stored password at all
  (board holds the password in RAM after pairing) — a Firmware-phase
  decision.
- **OPEN-3 (flash encryption + encrypted NVS, board-side execution)** is
  carried to the Firmware/OTA + Release phases: eFuse burn + dump
  verification on a sacrificial board first, then the production board,
  with closure criteria rewritten for the Rust series from the C#
  `FLASH-ENCRYPTION-PROCEDURE.md` (§5/§8 of that procedure). Until it
  closes, the key in NVS is plaintext — stated here, in the threat model,
  and in the release notes.

## 12. Signing keys — lifecycle (summary; detail in THREAT-MODEL §3)

- **Firmware image signing (Ed25519, locked — C# OPEN-17 CLOSED):** the
  existing keypair is reused (§1). Sign flow: release build → offline/CI
  signing with the private key from the CI secret (fail-closed — no secret,
  no build; unsigned firmware never ships) → signature + version + SHA-256
  in the manifest → **app verifies before upload** (`ed25519-dalek`
  `VerifyingKey::verify_strict`, baked public key) → **board verifies
  before apply** → release workflow verifies the signature and fails
  closed. Verify-before-apply is **Must**; on failure the old image keeps
  running. **Anti-downgrade:** only an equal or newer version is accepted
  (version scheme for the Rust series is redefined in the Firmware phase —
  it is not compared against C# v4.0.x; the eFuse-counter mechanism is
  C# OPEN-18, carried to Firmware/Release).
- **Tauri updater signing (Ed25519, dedicated keypair — §1):** new keypair
  via `tauri signer generate`. **Rotation rule (locked):** to rotate, ship
  an app build containing the **new public key first**, then sign updates
  with the new private key — otherwise old installs never accept an update.
  If the private key is lost, old installs are orphaned; keep the private
  key + password backed up offline, outside the repo, with the release
  owner. Updater behaviour: **auto-update opt-in, default OFF**; check only
  on user request; `latest.json` from GitHub Releases only; a failed
  signature verification rejects the update, fail-closed.
- **App code signing (OV certificate): DEFERRED — user decision 2026-11-13,
  carried (D-R11).** Rust v1.0.0 ships **unsigned**; a SmartScreen warning
  is expected and must be noted in the release notes. Users must **never**
  be told to disable SmartScreen. Firmware Ed25519 signing is unaffected
  by this decision.
- **Key compromise response (OPEN-19 / SEC-H-04):** the C# procedure
  (`FLASH-ENCRYPTION-PROCEDURE.md` §7 — Ed25519 rotation + USB reflash,
  Secure Boot revoke across its 3 digest slots, per-board flash-encryption
  key response, key loss) is **carried as a document to be rewritten for
  the Rust series** in the Release phase, with a board-side rotation/
  compromise drill at the A7-style real-board run. The doc review is not
  re-done here. See `THREAT-MODEL-RUST.md` §5.
