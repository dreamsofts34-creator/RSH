### DS-01 — P0 — App reports version 2.0.2, not 2.0.3; F23 wizard re-offer is inert for v2.0.2 skippers
- **Sources:** U-01, FC-04. **Files:** `Cargo.toml:55` (`version = "2.0.2"`), `crates/rsh-api/src/api.rs:22-24`, `crates/rsh-ui/ui/main.slint` (`app-version: "2.0.2"`), `crates/rsh-ui/src/main.rs:3625`.
- **Evidence:** `app_version()` returns `CARGO_PKG_VERSION`; markers are written `done/skipped 2.0.2`; F23 re-offer rule is `Skipped(v) => v != current_version` — a v2.0.2 skipper's marker equals the current version, so the wizard is never re-offered in v2.0.3. The release version check (`release.yml:171-180`) would also fail the tag.
- **Fix:** bump `[workspace.package] version` to `2.0.3` (+ `main.slint` default); audit every other hardcoded version (`src-tauri/tauri.conf.json` says `1.0.2` — see DS-71); add a gate check `app_version() == tag`. **Owner:** WS-C (UI).

### DS-02 — P0 — Tray "Restart wheel" panics the daemon's manager loop; loop dies silently, daemon looks alive
- **Sources:** B-01. **Files:** `crates/rsh-daemon/src/main.rs:265` → `crates/rsh-app-core/src/state.rs:2509-2524` (`restart_wheel`) → `state.rs:6682-6689` (`block_on_control`).
- **Evidence:** `restart_wheel` calls `block_on_control` (builds a fresh runtime + `block_on`) from inside the manager-loop tokio task. Proven empirically with a scratch tokio probe (`/tmp/tokio-probe`): `Cannot start a runtime from within a runtime`, task panicked. The `JoinHandle`s are discarded, so nothing restarts the loop; the daemon stays up (tray, IPC, engine run) but from then on: no watchdog, no retries, no pairing events, no tray-action draining (queued `TrayAction`s pile up unboundedly), no Wi-Fi rejoin. The panic hook logs to the diagnostics file only; the UI gets no signal.
- **Fix:** never call `block_on_control` from the manager loop — run it on `spawn_blocking` and await, or move "Restart wheel" to an IPC call (existing `spawn_blocking` dispatch path); defence-in-depth: keep the manager-loop `JoinHandle` and restart/log-fatally if it ends. Audit all other `block_on_control` callers (currently IPC-dispatch only, safe). **Owner:** WS-B (backend).

### DS-05 — P0 — F18 pipe-loop proof never executed: test script sets timeouts on a synchronous pipe
- **Sources:** FC-03, CI-03. **Files:** `tools/ci/windows-pipe-loop.ps1:38-51` (`Connect-PipeClient`).
- **Evidence (log `ci-pipe-loop.log`):** `daemon listening (pid 9120)` — daemon bound IPC fine; then `windows-pipe-loop.ps1: Exception setting "ReadTimeout": "Timeouts are not supported on this stream."` — thrown before any ping. `Connect-PipeClient` creates the stream with `[PipeOptions]::None` (synchronous) and then sets `ReadTimeout`/`WriteTimeout`, which .NET `PipeStream` rejects for a non-async pipe. ### DS-06 — P0 — No-board retry self-collides on UDP 4211, then latches a false "another app" error forever
- **Sources:** P-01. **Files:** `crates/rsh-app-core/src/state.rs` (forwarder `forward_with_retry`, ~7120 bind factory; ~7453 AddrInUse early-return), `crates/rsh-transport/src/udp.rs:340` (`bind_typed`, no `SO_REUSEADDR` by design), `crates/rsh-transport/src/port_conflict.rs` (F21 rule), `crates/rsh-daemon/src/main.rs` (manager loop `RetryTimer → activate_session`).
- **Evidence (MEASURED, reproduced 3/3 — 2× DEBUG, 1× RELEASE, sole RSH process):** clean repro, `ss -ulnp` shows UDP 4210/4211 free before start. Sequence: 4× HELO send failed → `HELLO timeout after 2250ms (attempt 3/3)` → `activation failed: Unreachable, retry in 2000 ms` → exactly 2 s later `activation failed: AddrInUse — "Another app is using the wheel port (UDP 4211) — close the old RSH app (RSH.exe)…"`, `retry in … none (user action required)`. At t=10 s `ss`/`/proc/net/udp` show NO 4211/4210 listener at all — the holder was this daemon's own first attempt: the retry's `bind(4211)` ran while the first socket was still bound, then the old transport was dropped and the forwarder exited on the F21 rule. Same in the UI-spawned daemon (~2 s after launch). Consequence: on any board-less machine the daemon reaches a terminal, user-action-required error ~5 s after launch with a WRONG diagnosis, and never retries.
- **Fix:** (a) tear down the old transport BEFORE the rebind (set shutdown flag, drop the `Arc<UdpSocket>`, join/await reader + HELO threads, then `bind`); or (b) bind UDP 4211 once per daemon lifetime and reuse the socket across attempts; (c) treat `AddrInUse` whose diagnosed holder is our own pid (or none) as transient/retryable with backoff instead of terminal; (d) put the `diagnose_udp_port_holder` result into the user-facing hint, not only `engine_status_detail`. **Owner:** WS-B (backend).

### DS-11 — P1 — AP-restart failures are swallowed: board can end up with no AP and no retry
- **Sources:** FC-10. **Files:** `firmware/net.cpp:287-297` (`net_lock_ap_wpa2_`), `:851-862` (`net_restart_ap_with_new_password`), `:538-545` (`net_maybe_rescan` tail).
- **Evidence:** all three AP-restart paths ignore the return values of `WiFi.softAP(...)`, `udpHello.begin(...)`, `udpCtrl.begin(...)` — unlike `net_start_ap_and_sockets` (net.cpp:330-341), which checks them. `net_lock_ap_wpa2_` sets `apIsOpen = false` unconditionally, so a failed WPA2 re-AP is believed to have succeeded and never retries; `netOk` stays `true`, so the 5 s `!netOk` retry branch never fires. A failed AP restart can leave the board unreachable until a manual reboot, with no log/LED signal.
- **Fix:** check every `softAP`/`begin` return in these three paths; on failure keep `apIsOpen` as-is (or set a retry flag), log a `RSH_DIAG_*` event, and retry on the next `net_poll()` / clear `netOk` so the existing 5 s retry path engages. **Owner:** WS-D (firmware).

### DS-13 — P1 — No cross-check between the baked OTA pubkey and the release signing secret
- **Sources:** FC-05. **Files:** `firmware/signing_pubkey.h:30` (+ identical copy `firmware/rsh/signing_pubkey.h:30`); `firmware/webota.cpp:51,324`; `.github/workflows/release.yml:320-326,355`.
- **Evidence:** the release "Verify firmware" step verifies the OTA signature only against the pubkey derived from the `RSH_SIGNING_KEY_PEM` secret. Nothing compares that pubkey to the baked `kRshSigningPubkey` the board actually verifies against. If the secret is ever rotated (or the header goes stale), the release stays green while every board rejects every OTA image (not a brick — old firmware keeps running — but OTA is dead with no release-side signal). Verified today: the baked key is internally consistent (SHA-256 `387764a4…a6411`, matches its documented fingerprint; the two header copies are byte-identical). The gap is the missing check, not a current mismatch.
- **Fix:** in `release.yml` "Verify firmware", derive the header from the secret and `diff` it against `firmware/signing_pubkey.h` (delete the duplicate header or generate both from one source). Fail closed on any difference. **Owner:** WS-D (firmware/CI).

### DS-14 — P1 — Windows pipe-create "in use" retry is UNBOUNDED: a squatted pipe leaves the daemon IPC-dead forever
- **Sources:** B-02. **Files:** `crates/rsh-daemon/src/main.rs:651-656` (`pipe_in_use_backoff`), `:696-737` (`create_pipe_listener`).
- **Evidence:** `record_failure(in_use=true)` always returns `RetryAfter(backoff)` (capped at 1 s) and never counts toward the 5-failure fatal. If the pipe name is held by anything that never accepts, the daemon loops `create → fail → sleep ≤1 s → log` forever: no IPC, no fatal status, no exit, one log line per second indefinitely.
- **Fix:** cap total in-use retry time (e.g. fatal after ~60–120 s of continuous in-use failures, writing the fatal status like the 5-attempt path), or at least go quiet after the first few log lines with a periodic heartbeat line. Same shape as the F20-C1 fix (DS-33). **Owner:** WS-B (backend).

### DS-15 — P1 — `rejoin_wifi` runs blocking, timeout-less `netsh` calls on the manager-loop tokio task (F14 — deferred, still open)
- **Sources:** B-03. **Files:** `crates/rsh-daemon/src/rejoin.rs:187-218`, called from `crates/rsh-daemon/src/main.rs:439-447` (manager loop, on Active transition).
- **Evidence:** two sequential `Command::output()` calls with no timeout. `netsh wlan connect` can block for many seconds when the Wi-Fi stack is in a bad state. While it runs, the 250 ms manager-loop ticker stalls: watchdog, retry timer, tray-action drain, pairing-event publishing all pause. Already recorded as deferred F14 in the v2.0.3 plan.
- **Fix:** move the rejoin to `spawn_blocking` (or a dedicated thread) with a hard timeout (e.g. kill after 30 s), or run it as an async child-process wait. (Profile XML fixed temp path is DS-45.) **Owner:** WS-B (backend).

### DS-16 — P1 — `start_engine` no-ops when the supervisor thread is dead: a dead engine never recovers without a process restart
- **Sources:** B-04. **Files:** `crates/rsh-app-core/src/state.rs:3816-3820` (`start_engine`), `:3996-4023` (`stop_engine`).
- **Evidence:** `start_engine` returns `Ok(())` immediately `if lock(&self.engine_thread).is_some()`. The stored `JoinHandle` is never liveness-checked (`is_finished()` is never called on it anywhere). If the supervisor thread panicked or exited early (e.g. the 5 s `ready_rx` timeout path at `state.rs:3832-3847`, which records `Failed` but keeps the handle), every later `start_engine`/`connect_transport` claims the engine is running while it is dead.
- **Fix:** in `start_engine`, treat a finished handle as absent (take it and re-spawn), and/or add a supervisor liveness check to `engine_status()` so a dead supervisor surfaces as `Failed` with a user Retry. **Owner:** WS-B (backend).

### DS-17 — P1 — IPC server drops the whole client connection on one lagged broadcast event
- **Sources:** B-05. **File:** `crates/rsh-ipc/src/server.rs:133-150` (`serve_stream`, `event_rx.recv()` arm).
- **Evidence:** `broadcast::Receiver::recv` returns `Err(RecvError::Lagged(_))` when the subscriber falls behind the 256-capacity channel; `Lagged` is treated identically to `Closed`: the entire connection is torn down. The UI must reconnect and re-subscribe; a burst of events during a UI stall is exactly when this fires.
- **Fix:** on `Lagged`, skip to the newest event (continue the loop / drain with `try_recv`) instead of breaking; only break on `Closed`. **Owner:** WS-B (backend).

### DS-18 — P1 — Daemon reports "Connected" label while the manager state is Backoff/Connecting
- **Sources:** B-06. **File:** `crates/rsh-daemon/src/daemon_api.rs:150-168` (`connection_from`, `other` branch).
- **Evidence:** for any non-Active, non-Error manager state, the label is `"Connected"` whenever `transport_state.session_active && transport_state.state == CoreState::Connected` — regardless of manager state. Reachable when the watchdog fires (manager → `Backoff`) before `disconnect_transport()` runs. The comment above it claims the opposite ("never 'Connected'"), but the code upgrades the label instead of downgrading it.
- **Fix:** derive the label from the manager state alone when it is not Active; only use the transport's Connected as the label when the manager is Active. Add a unit test asserting `label != "Connected"` for every non-Active manager state. **Owner:** WS-B (backend).

### DS-19 — P1 — `IpcApi::ping` + slow-poller fail-fast can wedge the health monitor's view
- **Sources:** B-07. **Files:** `crates/rsh-ui/src/ipc_api.rs:356` (`ping`), `:334-344` (`call_async` fail-fast on `link_dead`), `:283-293` (fast poller sets `link_dead` on ONE failed `poll` round), `crates/rsh-ui/src/main.rs:6660-6700` (health monitor).
- **Evidence:** `link_dead` is set on a single failed `poll` round — including one 500 ms timeout caused by the daemon being briefly busy (e.g. a `set_output_backend` UAC wait holding the single-flight IPC lock). Once set, all UI write calls fail instantly with `Closed` until the poller succeeds again; the health monitor's `ping()` still works, so the monitor may keep reporting "alive" while every action errors.
- **Fix:** require N consecutive failed poll rounds (e.g. 2–3, ~1–1.5 s) before setting `link_dead`, and/or exempt the fail-fast while a long call (`set_output_backend`, 75 s) is in flight. Verify against the health-monitor debounce (`PING_DEBOUNCE`, ~3 s) so the two death detectors agree. **Owner:** WS-B (backend).

- **Sources:** P-11. **File:** `crates/rsh-ui/src/main.rs` (70 `eprintln!` outside tests, incl. `log_event` at `:6438`). **Fix:** route UI event logging through the same buffered diagnostics log as the daemon (or gate behind a verbose flag); never `eprintln!` per event on the UI thread. **Owner:** WS-E.

### DS-80 — P2 — Single-flight IPC lock: one slow call stalls every other call for up to its timeout
- **Sources:** P-12. **Files:** `crates/rsh-ipc/src/client.rs:290`, `crates/rsh-ui/src/ipc_api.rs:262,291`. **Fix:** give the fast poller its own connection (second socket/pipe) so liveness polling can never queue behind — or in front of — user actions; or add a priority lane (job calls pre-empt the poller's next cycle). **Owner:** WS-E.

### DS-81 — P2 — Startup does store + backend + autostart work serially before the tray; autostart sync re-reads settings repeatedly
- **Sources:** P-13. **File:** `crates/rsh-daemon/src/main.rs` (`main`: store open → runtime → IPC → engine start → `activate_startup_backend()` → autostart heal + `sync_autostart`).
- **Evidence (MEASURED total, STATIC breakdown):** total cold start to IPC answer is only 107 ms median (DEBUG), so this is not a user-visible problem today. The autostart block does ≥3 `settings()` clones + a Run-key/`.desktop` read + a possible write on every launch, and `activate_startup_backend` probes vJoy (DLL load attempt) on the startup path.
- **Fix:** read settings once into a local, do the autostart sync + backend activation concurrently with (not before) tray creation, or defer both until after the first IPC answer. **Owner:** WS-E.

### DS-82 — P2 (new, enabling) — Instrumentation: frame-time + IPC latency histograms
- **Sources:** perf scan §3 (frame-budget p99 UNMEASURED; IPC tails only probed externally).
- **Evidence:** there is no frame-time instrumentation (50 ms Slint timer, `push_frame`, render thread have no timing); the rig samples window presence at 100 ms, not frame durations; Xvfb uses llvmpipe, so local render-time numbers would not represent the user's GPU anyway.
- **Fix:** add an `Instant` around `push_frame` + a render-completion timestamp and export p50/p99 in Diagnostics; add a per-method IPC latency histogram in the daemon (or at least a `diag_stats` counter). Do not present the 50 ms timer period as a frame time. **Owner:** WS-E.
